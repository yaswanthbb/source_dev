## Data and write safeguards

- Existing endpoints only: account GET `/users/me`, public article list/detail GETs, POST `/articles`, DELETE `/articles/:id`. Timed/abortable entry reads; no automatic retries, focus or reconnect refetch. No mount-time write, generation or provider call. The existing authenticated layout still owns access gating.
- Query keys include the cached account ID/role, never a token. Fresh account validation and session snapshots protect loads and write preflights. Changed account/access/invalid metadata hides cached articles and the draft; account changes require a page reload. Library rows are exact author-ID matches even for admins. Other authors and orphaned articles do not appear in My articles.
- Strict owned metadata projection drops article bodies and full returned account objects from the library. IDs, titles, timestamps, ownership and optional link metadata are checked. Missing/invalid contracts are unavailable, not silently empty. Account metadata reuses the established normalized workspace user shape.
- Publishing validates fields and freshly checks account/library, sends one POST, validates the response against author/title/exact Markdown/links, then reads the public detail and own library back before reporting success. Known created IDs are retained even when acknowledgements/readback fail. No optimistic row or automatic navigation/input clearing.
- Deletion freshly checks account/list ownership and selected saved fingerprint, then checks detail metadata before one DELETE. A boolean success acknowledgement, actual detail 404 and absence from a checked own list are all required for confirmed removal. Changed/removed/foreign rows stop before deletion; an admin using My articles cannot select another author's row.
- Synchronous busy guard blocks repeated in-flight actions. Network/408/5xx/malformed ACK or failed readback is ambiguous; all writes pause. Recovery is read-only, retains operation context/known ID and checks only current own records. Possible new title matches exclude the pre-request IDs and foreign owners; a matching row is not claimed as proof that this exact request completed.
- Failed recovery stays locked. A successful check still requires explicit user review before resuming; the earlier-request/duplicate warning remains afterward. Deletion recovery only treats actual 404 as absence, never HTTP/transport failure. An earlier request can still finish after a check. No backend idempotency, cross-tab serialization or atomic identity/fingerprint guarantee is claimed.
- Fixed safe errors discard Axios response/request/config bodies rather than retaining or rendering backend messages. No backend, schema, migration, dependency or terminal-command changes.
